# v174 independent data-safety audit — 2026-11-02

Scope: source-level review of `main` at merge commit `16c89366833df8838be849ef4e5d8c2c20a6ea9b`. This is **not** a live, authenticated, two-device test. No production data or credentials were accessed. The audit is independent of Claude's 38-test report.

## Verified architecture

- `index.html` uses `syncSnapshot` to select `poly_*` and `leren_*` localStorage keys, excluding per-device credentials/settings through `SYNC_SKIP`.
- Firebase Auth supports Google sign-in and passwordless e-mail link. The browser accesses its own Firestore `users/{uid}` document with an ID token.
- Firestore write uses `currentDocument.updateTime` precondition and retries conflicts by fetching, merging and writing. This is a useful concurrency guard, **not proof of lossless semantic merging**.
- `backupData()` exports a v3 JSON snapshot of synced keys. v3 restore uses `syncMerge({}, current, backup)`; v2 restore uses an older separate path.
- `firestore.rules` restricts `users/{uid}` to the authenticated owner and caps the `blob` at 900,000 characters (verify deployed rules match this repository).

## Findings and actionable checks

### HIGH — Old v2 backups can overwrite newer progress

In `index.html`, `backupRestore` v2 branch assigns `store=data.store`, `score=data.score`, and overwrites the pathway/reward records via `lsSet`. It does not merge those data with the current state. The UI says restored progress retains newer results, but the v2 branch can contradict that. Fix by migrating v2 payload into the same validated merge pipeline and explicitly test restoration into newer v174 progress. Until fixed, do not claim *all* old backups merge safely.

### HIGH — v3 backup validation is insufficient for a lossless safety promise

A v3 backup is accepted if `app`, `v`, and `keys` are present and `keys` is any plain object. Its values are only checked to be strings for keys allowed by `syncable`. There is no payload integrity checksum, size limit, strict field schema or full preflight validation before mutations, and per-key write errors are ignored. A malformed but syntactically valid backup can be partially applied. Add versioned schema validation, an integrity digest, a size limit, and an all-or-nothing/rollback restore path with explicit error feedback. Preserve compatibility with legitimate v2 and v3 files.

### HIGH — Concurrent activity counters can lose increments

`syncMergeVal` merges any conflicting numeric values using `Math.max`. If two devices independently increase a metric from 10 to 11, the merged count is 11 rather than 12. This affects counters such as per-skill answers, speaking attempts and learning time on the same calendar day. Current `tests/sync-v174.cjs` explicitly expects the maximum, not the sum. Do not promise that every activity event survives a simultaneous two-device merge. Consider idempotent event IDs or per-device counters, with deterministic merge and bounded retention.

### MEDIUM — Field-specific merging needed for some learning state

`leren_path_v1` is special-cased, but the code takes all other root fields from local and only merges `completed` and `mistakes`. Consequently, simultaneous changes to independent per-course `entries`, `parked` and the active session could be lost. Separately, generic array merging treats removal of an item on either side as authoritative, which should be checked for review queues and mistakes. Design explicit conflict rules for each data type, test concurrent independent A1.1/A1.2 progression, and preserve the most recently active session where safe.

### MEDIUM — Cloud payload capacity and silent sync failures

`firestore.rules` limits `blob` to 900,000 characters. `syncPush` ignores the return value `"error"` from `syncWrite` on non-conflict failures. The UI should clearly signal unsynced changes and retry on network/permission/size errors; add tests for the 900,000-character cap and denied writes. Verify deployed Firestore rules.

### MEDIUM — Local data must not be confused with cache

Clearing only Cache Storage and unregistering a service worker ordinarily does not clear localStorage; deleting site data does. The app's backup reminder is useful, but browser storage persistence is best-effort and does not protect against manual site-data deletion. Do not describe local storage as permanent.

## Suggested test matrix before final release sign-off

1. Two isolated signed-in browsers with the same account, simultaneously advancing different A1.1/A1.2 lessons: both remain completed.
2. Two browsers independently adding correct/incorrect answers to the same skill and minutes on the same day: reconcile *all* events or clearly disclose count semantics.
3. Restore a v2 backup into a newer account with more XP, newer test results and lessons: nothing regresses.
4. Restore a damaged v3 file: no partial mutation.
5. Restore a valid v3 file twice: no duplicated XP or awards.
6. Offline edits on both devices, then online sync in both orders; force a Firestore precondition conflict.
7. Inject 400/403/429/500 and the 900,000-character limit: visible sync error and safe retry.
8. Sign out on a shared device and sign in to a different account: explicitly test whether old local user data are visible or synced into the new account; define product policy.
9. Test old browsers and both language levels; complete a fresh lesson, exam and SRS warm-up after restore.
10. Confirm real Google/e-mail authentication, deployed rules and cross-device replication. Mocked VM tests alone cannot establish production service reliability.

## Recommendation

**Conditional / not yet signed off for fully lossless cross-device sync.** The main architecture is present and authenticated but the documented edge cases need corrective changes and integration tests. Prioritize v2 backup overwrite and corrupt-backup atomicity, then concurrency semantics and explicit sync error reporting.
