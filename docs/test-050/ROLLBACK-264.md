## Чому відкат — це не «просто повернути 264»

273 зберігає ім'я учня (`leren_learner_name`) і план дня (`leren_today_v1`) **лише на пристрої**. Код 264 цих ключів не знає і вважає їх звичайним прогресом:

- у вошедшого в акаунт учня ім'я пішло б у Firestore;
- ім'я потрапило б у файл резервної копії.

Це перевірено мутацією: тест відкату з кодом 264 падає саме на цьому.

Тому відкат іде на **збірку 274** = код 264 + ці два ключі в `SYNC_SKIP` + власний номер версії (`leren-be-v274`, `app.js?v=274`). Більше нічого не змінено.

- Гілка: `claude/rollback-274` (worktree `/Volumes/Ai_Project/LerenBe-rollback-274-2026-11-25`), поки локально.
- Тест: `tests/rollback-273-274.cjs` — 264 → 273 → 274 → 273 зі справжнім Service Worker, 2 профілі (учень з 264; новий учень, що почав на 273 з ім'ям і незавершеним уроком). Усі пройшли:
  - кожен ключ, залишений 273, збережено байт у байт (значки можуть лише додаватися);
  - XP і пройдені уроки ті самі;
  - ім'я і план дня не синхронізуються і не потрапляють у резервну копію;
  - інтерфейс 264 працює онлайн і офлайн, кеш лише v274;
  - після повторного переходу на 273 повертаються «Сьогодні», ім'я, прогрес EN і незавершене заняття.

## Відкат (≈10 хв до сайту, далі — у міру відкриття застосунку учнями)

Коли: втрата або псування прогресу, застосунок не відкривається, масові помилки, урок не можна пройти. Дрібні вади — краще виправлення 275, а не відкат.

```bash
git fetch origin
git switch -c rollback/to-274 origin/main
git revert -m 1 <SHA злиття 273> --no-edit       # дерево повертається до 264
git cherry-pick <коміт гілки claude/rollback-274>  # 264 → 274: два ключі лише на пристрої + версія
git diff --stat claude/rollback-274 HEAD           # очікувано: порожньо або лише docs/
git push -u origin rollback/to-274
gh pr create --base main --head rollback/to-274 --title "Rollback 273 → 274 (код 264)"
```

Злити цей PR (з вашого дозволу) → GitHub Pages публікує 274 за 1–3 хв.

Що відбувається на телефонах:

- Застосунок перевіряє оновлення при відкритті і кожні 30 хв.
